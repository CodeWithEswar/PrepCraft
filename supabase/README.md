# Supabase Database Infrastructure & Operations

Supabase PostgreSQL is PrepCraft's single authoritative system of record. It owns user identities, workspaces, membership, the canonical question catalog, user attempts, revision schedules, study plans, job applications, interview history, and file metadata.

---

## 1. Directory Structure

```text
supabase/
├── config.toml           # Local Supabase CLI configuration (PostgreSQL 15)
├── migrations/           # Authoritative, immutable, timestamped SQL migrations
├── seed/                 # Development-safe, idempotent canonical catalog seeds
├── functions/            # Supabase Edge Functions (external webhooks, privileged adapters)
├── policies/             # Human-readable RLS rationale grouped by domain
│   ├── README.md
│   ├── workspaces.md
│   ├── practice.md
│   ├── interviews.md
│   └── applications.md
├── tests/                # Automated pgTAP database test suite
│   ├── sql/              # Schema invariants, triggers, functions, constraint tests
│   └── rls/              # Tenant isolation, member, non-member, cross-workspace tests
└── README.md             # This operational guide
```

## 2. Local Setup & Workflow

### Prerequisites
- Docker Desktop (active and running)
- Supabase CLI (`2.84.2` or later)

### Common Commands

```bash
# Start local Supabase services (PostgreSQL, Auth, Storage, Studio)
supabase start

# Check status of local services
supabase status

# Stop local Supabase services
supabase stop

# Check migration naming conventions (static check)
npm run db:check

# Run SQL linter across migrations
npm run db:lint

# Execute pgTAP test suite (SQL constraints + RLS isolation)
npm run db:test
```

The local Supabase Studio dashboard is available at `http://localhost:54323` when running.

## 3. Migration Workflow

Migrations represent the immutable, ordered history of schema evolution.

### Creating Migrations
Use timestamped filenames generated by the Supabase CLI:
```bash
supabase migration new <name_of_migration>
```
Example: `supabase/migrations/20261024120000_create_profiles.sql`.

### Migration Standards
1. **Ordered & Immutable**: Migrations deployed to staging or production must NEVER be edited retroactively.
2. **Comprehensive**: Include tables, columns, foreign keys, CHECK constraints, UNIQUE constraints, indexes, triggers, SQL functions, RLS enablement, and RLS policies in the migration.
3. **Rollback & Safety**: Write backward-compatible migrations. Avoid destructive operations without a phased transition.
4. **No Placeholders**: Do not create empty migration files.

## 4. Reset & Seed Workflow

### Resetting Local Database
```bash
# Drops public schema, reapplies all migrations in order, and executes seed scripts
supabase db reset
```

### Seeding Guidelines
- `supabase/seed/` is strictly for **development-safe canonical catalog data**:
  - DSA tracks, patterns, difficulty tiers, and curated problem references.
  - Core curriculum topics (Java, DBMS, OS, Networks, System Design).
  - Standard company preparation roadmaps.
- **Idempotency**: Use `ON CONFLICT DO NOTHING` or stable UUIDs so seeding can be re-run safely.
- **Forbidden in Seed**:
  - NO real candidate personal information.
  - NO production secrets or mock credentials.
  - NO fabricated application histories that could be confused with live data.

## 5. Row Level Security (RLS) Architecture

PrepCraft implements strict **Defense in Depth**:

```text
Client capability hint
        ↓
Server Action / Route authorization
        ↓
Domain service business rules
        ↓
PostgreSQL constraints & triggers
        ↓
Supabase PostgreSQL Row Level Security (RLS)
```

### RLS Invariants
1. **Always Enabled**: Every table created in the `public` schema MUST have RLS enabled:
   ```sql
   alter table public.<table_name> enable row level security;
   alter table public.<table_name> force row level security;
   ```
2. **Workspace Isolation Pattern**:
   All tenant-owned tables enforce membership via `workspace_members`:
   ```sql
   workspace_id in (
     select workspace_id from public.workspace_members
     where user_id = auth.uid()
   )
   ```
3. **No Drift**: `supabase/policies/` contains human-readable architectural explanations. Migrations are the sole deployment authority.

## 6. Database Tests (pgTAP)

Tests under `supabase/tests/` prove schema invariants and access control before code reaches production:

- `tests/sql/`: Validates column nullability, check constraints, foreign key cascades, unique constraints, and SQL functions.
- `tests/rls/`: Validates tenant isolation using simulated authenticated roles (`anon`, `authenticated` with specific `auth.uid()`):
  - Owner can access.
  - Authorized member can access.
  - Non-member is blocked (0 rows returned or permission denied).
  - Cross-workspace read/write fails.
  - Disabled/removed member is blocked.
  - Anonymous callers are blocked where prohibited.

Run the test suite with:
```bash
npm run db:test
```

## 7. Generated TypeScript Types

Types are generated directly from the local PostgreSQL schema to ensure zero drift between the database and application code:

```bash
supabase gen types typescript --local --schema public > src/lib/supabase/types.ts
```

- When no application migrations exist, `src/lib/supabase/types.ts` exposes an explicit pre-schema placeholder.
- Never manually edit generated types to bypass type errors or hide schema mismatches.

---

## 8. SQL Functions vs Edge Functions

Do not confuse PostgreSQL functions with Supabase Edge Functions:

- **PostgreSQL Functions (`supabase/migrations/`)**:
  Stored procedures, triggers, audit logging, computed invariants, and atomic multi-table state updates running inside the PostgreSQL engine.
- **Supabase Edge Functions (`supabase/functions/`)**:
  Deno/TypeScript functions running at the edge. Used ONLY when a concrete boundary requires external HTTP execution near Supabase (e.g. third-party webhooks, specialized provider integrations). Regular application business logic belongs in `src/features/<feature>/services/` or Next.js server actions.

---

## 9. Security & Secrets Management

1. **Service-Role Key**: The `SUPABASE_SERVICE_ROLE_KEY` has full superuser bypass privileges over RLS. It must NEVER be exposed to the client, placed in browser code, or committed to Git.
2. **Client Environment**: Only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are safe for client-side configuration.
3. **Never Commit Secrets**: Secrets must remain in `.env.local` (local development) and platform secret managers (production).
